## 1. 项目总体定位

当前项目是一套面向“担保业务演示”的 Next.js Demo 系统，核心不是单一页面，而是把几条业务线放在同一个工作台里：

1. 代偿补偿单案件审查与审批表生成
2. 代偿补偿简报预览
3. 担保体系简报预览
4. 机构评价报告生成
5. 授信报告生成
6. AI 复核工作台
7. 授信报告数据核验 / 来源映射

左侧导航定义在 [Sidebar.tsx](/Users/xipilabs/dev/Experiment/demo_sxzd/components/Sidebar.tsx)。

## 2. 运行架构

### 2.1 技术栈

当前项目的主技术栈如下：

1. 前端与服务端同构框架：Next.js App Router
2. 页面组件：React + TypeScript
3. 数据校验：zod

## 3. AI 调用总入口

统一的大模型调用封装在 [blackwhite.ts](/Users/xipilabs/dev/Experiment/demo_sxzd/lib/server/blackwhite.ts)。

### 3.1 当前环境变量

当前严格要求以下环境变量存在：

1. `BLACKWHITH_APPID`
2. `BLACKWHITH_KEY`
3. `BLACKWHITH_BASE_URL`
4. `BLACKWHITH_MODEL`

说明：

1. 这些变量使用 zod 强校验，缺失会直接报错，不存在“读不到就换方案”的兜底。
2. `BLACKWHITH_MODEL` 支持配置，未显式提供时默认值为 `google/gemini-2.5-flash-lite`。

### 3.2 当前调用方式

当前统一调用链路有两层：

1. `blackwhiteChat(messages, options)`：普通文本对话
2. `blackwhiteJson(schema, messages, options)`：先拿文本结果，再提取 JSON 并用 zod 校验

因此，项目里凡是“需要稳定结构化输出”的能力，基本都是：

1. 构造 system / user prompt
2. 调 `blackwhiteJson`
3. 用 zod 严格校验输出
4. 校验失败直接报错

这符合当前仓库对核心功能“不允许兜底”的要求。

### 5.3 核心服务实现

主实现文件：

- [case-analysis.ts](/Users/xipilabs/dev/Experiment/demo_sxzd/lib/server/case-analysis.ts)

它负责：

1. 读取真实案件目录
2. 枚举 PDF / Excel 文件
3. 抽取文档文本或摘要
4. 识别材料清单匹配状态

### 5.4 当前缓存策略

这里有两层缓存：

1. 原始提取缓存
2. 深度分析缓存

版本常量位于 [case-analysis.ts](/Users/xipilabs/dev/Experiment/demo_sxzd/lib/server/case-analysis.ts)：

1. `EXTRACTION_CACHE_VERSION`
2. `ANALYSIS_CACHE_VERSION`

也就是说，只要版本号不变，且原始签名未变化，就优先命中已有缓存。

### 5.5 工作台步骤

工作台不是多个平级页面，而是一个案件工作台按步骤推进。当前主要步骤包括：

1. `overview`
2. `integrity`
3. `verify`
4. `document`
5. `review`

### 5.6 步骤说明是怎么来的

当前每个步骤顶部的“本步分析结论”不是写死的，它来自 [step-artifacts.ts](/Users/xipilabs/dev/Experiment/demo_sxzd/lib/server/step-artifacts.ts)。

实现方式是：

1. 将 `CaseAnalysis` 中的材料、规则、风险、草稿摘要组织成 payload
2. 按步骤拼不同的 prompt
3. 调 `blackwhiteJson`
4. 生成：
   - `summary`
   - `highlights`
   - `callouts`
5. 再缓存到：

```text
.cache/demo-analysis/step-artifacts
```

### 5.7 代偿补偿审批表生成

审批表生成核心在：

- [compensation-approval-report.ts](/Users/xipilabs/dev/Experiment/demo_sxzd/lib/server/compensation-approval-report.ts)

该模块当前做了三件事：

1. 把案件分析结果整理成适合审批表的结构化输入
2. 结合 prompt-config 生成正式审批表内容
3. 输出结构化结果，再由前端渲染成审批表版式

说明：

1. 它不是让模型直接输出整页 HTML。
2. 它让模型输出结构化 JSON，再由前端渲染。
3. 这样可以保证版式更稳定。

## 13. 当前演示时应该如何解释

如果是面向客户或管理层演示，当前最准确的讲法应当是：

### 13.1 真实 AI 主链路

以下是当前真实由 AI 参与的核心链路：

1. 代偿补偿案件材料分析与步骤结论
2. 代偿补偿审批表生成
3. 授信报告生成
4. 机构评价报告生成
5. AI 复核

### 13.2 模板化演示链路

以下模块当前仍是模板 / 数据替换，但页面已经具备 AI 指令展示能力：

1. 担保体系简报
2. 代偿补偿简报

更准确的说法是：

1. 页面右侧展示了“如果这两类简报改造成 AI 成文，会给模型什么要求、参考什么模板、参考什么资料”
2. 但底层当前仍使用模板渲染器，不应对外声称它们已经改造成 LLM 实时成文

## 14. 当前局限与注意事项

### 14.1 代偿补偿模块

1. 当前更适合演示单案件审查闭环，不是通用案件平台
2. 材料目录、案例数据和页面文案高度围绕宝鸡三家村案例

### 14.2 机构评价与授信报告

1. 更适合演示“结构化数据 + 模型成文”
2. 不适合作为通用多租户报告平台直接上线

### 14.3 两类简报

1. 目前仍是模板驱动
2. 页面上的 AI 指令面板主要用于演示
3. 如果后续要改成真 AI 生成，需要再把 prompt-config 真正接进生成链路

### 14.4 环境与依赖

1. `blackwhite` 环境变量必须完整
2. Excel、docx、PDF 解析路径依赖本机文件结构
3. 本 Demo 偏“本机演示工程”，不是无状态纯云端架构

## 16. 结论

当前这个项目不是“所有东西都由 AI 生成”的统一 Agent 平台，而是：

1. 代偿补偿、授信报告、机构评价报告这三条线已经有比较明确的 AI 主链路
2. 两类简报当前仍是模板驱动，但页面已具备 AI 演示包装
3. AI 复核是统一工作台，用于对前述文档做二次检查、追问和经验沉淀

如果后续要继续完善，最值得继续做的不是再加新页面，而是：

1. 把两类简报从模板驱动升级为真 AI 成文
2. 把 prompt-config 真正接入简报生成链路
3. 把更多生成结果统一纳入 AI 复核和来源映射体系
